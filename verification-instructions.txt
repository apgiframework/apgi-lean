The central design decision is to separate the canonical specification from the proof library.

`generate_lean.py` generates definitions and constants only from the registry, never proofs. Hand-written proofs import those definitions, so a change to the spec breaks a proof loudly. Each theorem's report entry records the equation ID and the registry hash it was proved against.

The canonical registry defines what APGI claims mathematically. Lean verifies consequences of those definitions. Python tests their numerical realization. Experimental data assesses their scientific relevance.

Theorem–test pairing
Every Lean theorem gets a twin Hypothesis property test that checks the same statement against the Python implementation, with a tolerance for float64. Lean establishes the mathematics; the twin test checks that the code obeys it.

Precondition coverage
CI checks that every registry range sits inside the hypotheses of the theorem that covers it. For example, a theorem that needs dt ≤ τ is useless if the registry allows dt > τ. A precondition that cannot be checked because a value is missing is reported as an open conflict, not as a pass.

5. What to formalize first
I recommend five small proofs, in the following order.
Proof 1 — Ignition threshold monotonicity
For a simplified criterion:
\[
I(S,\theta) \iff S>\theta
\]

Prove:
\[
\theta_1\leq\theta_2
\land I(S,\theta_2)
\implies I(S,\theta_1)
\]

This establishes that a higher threshold cannot make ignition easier when the signal is held fixed.

The theorem is mathematically straightforward. Its APGI relevance depends on the canonical definition of ignition.
Proof 2 — Threshold semantics: floor versus operating range
Use two types. `ThresholdState` respects the 0.5 AU floor. `OperatingThreshold` lies within [2, 8] AU.

Then prove two things. The clamped update preserves the floor. It does not preserve the range for targets below 2 AU, but it does preserve the range when targets are restricted to [2, 8] AU and 0 ≤ gain ≤ 1.

Lean thereby forces the specification to decide whether [2, 8] is a state invariant (and restrict admissible targets) or a regime label. This settles the P0 θₜ conflict formally instead of leaving it as prose.
Proof 3 — Cusp sign convention
For a candidate potential:
\[
V(x)=\frac{x^4}{4}+\frac{a x^2}{2}+\theta x
\]

the derivative is:
\[
\frac{dV}{dx}=x^3+ax+\theta
\]

Lean can verify this symbolic relationship.

However, it cannot independently establish that this is the scientifically intended APGI potential.

The candidate potential uses the corrected +θₜ·x sign. A Python check flags any document still showing −θₜ·x.

Add the lemma "a ≥ 0 ⇒ unique equilibrium". It shows that a < 0 is necessary for hysteresis, which links to the Innovation 4 hysteresis prediction. It is not sufficient: three equilibria also need 4a³ + 27θ² < 0. Any paper that cites the Lean result must word it as "necessary".

First verify the canonical equation and sign convention; then prove the derivative and equilibrium identities.
Proof 4 — Discrete update invariance
For a simplified allostatic update:
\[
x_{t+1}=x_t+g\,(u_t-x_t)
\]

prove that if
\[
x_t,u_t\in[lo,hi],\quad 0\leq g\leq1
\]

then
\[
x_{t+1}\in[lo,hi]
\]

The gain is written g (`gain`), not α, because α collides with sigmoid steepness.

Add the forward-Euler form with g = dt/τ. It is bounded whenever dt ≤ τ. That is the precondition the integrator actually has to honour.

This is a practical example of a bounded-state invariant.

It does not establish stability of the full APGI model, but it provides a foundation for checking individual update components.
Proof 5 — Dimensional consistency
Represent physical units explicitly and reject incompatible additions or conversions.

This may provide more practical value than abstract epistemic tier types.

For example, a dimensionless coefficient cannot be silently treated as a rate with units of inverse seconds.

Make AU its own base dimension, so it cannot mix with any physical unit until a calibration map exists. Add a regression test that rejects κ typed as mol ATP/bit.

Use separate types for physical dimensions and epistemic classifications. They solve different problems.

Negative cases are tests, not comments. Each forbidden unit mix must be shown to fail to elaborate, using `fail_if_success` (or `#guard_msgs`) around the bad expression.

Pilot completion criteria
The pilot passes only when:
- Every canonical parameter has a source identifier, unit, version, and documented range.
- Known discrepancies produce explicit failures.
- The selected Lean theorems compile without sorry or unapproved custom axioms.
- Mathematical results are linked to exact specification revisions.
- Python tests pass the existing APGI numerical tolerances, including the specified \(10^{-9}\) checks where applicable.
- Continuous integration produces a reproducible verification report.
- No mathematical proof is described as empirical confirmation of APGI.

`make_report.py` evaluates each criterion from build artefacts and prints which are met.

The Lean installation workflow using lake new apgi math, Mathlib's precompiled cache, and lake build is supported by the current documentation. Pin the toolchain and dependency versions for reproducibility. `lean-toolchain` (v4.36.0) and `lake-manifest.json` (Mathlib fc4f59e…) are the pins; do not run `lake update` casually.

7. Cost-benefit analysis
Planning estimates, not measured implementation times.

- Canonical registry and validation: 1–3 days. Expected benefit: very high.
- Source extraction and comparison: 2–5 days. Expected benefit: very high.
- Lean project and basic proofs: 2–4 days. Expected benefit: high.
- Python integration and CI: 2–4 days. Expected benefit: high.
- Discrete-update invariants: 3–7 days. Expected benefit: medium–high.
- Full L0–L4 formalization: unbounded research effort. Expected benefit: uncertain.

A small pilot is reasonable. Full-system formalization is not justified at the current stage.

The main risk is spending time proving elementary mathematical facts while unresolved specification conflicts and empirical-validation tasks remain open.
8. Final recommendation
Adopt the revised approach with a strict scope limit.

I would allocate approximately 80% of the initial effort to canonical specification consistency, source traceability, and Python regression testing, and 20% to Lean.

The first milestone should be the automatic detection of the θₜ and notation conflicts. The second should be a successful Lean proof tied to a canonical APGI equation.

Do not expand to full L0–L4 verification until the pilot demonstrates that formalization catches defects ordinary tests would miss.

Final assessment: design 85/100; implementation 60/100 (5 of 7 pilot criteria met locally). Re-rate after the first green CI run and resolution of the P0 author decisions. This is a rating of engineering suitability, not of APGI's scientific validity.

The strongest result would be a system in which every major APGI claim can be traced through:

Source → Canonical definition → Mathematical proof or test → Python implementation → Empirical evidence → Verification status.
